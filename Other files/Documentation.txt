================================================================================
WIENER NEUSTADT SHUNTING YARD SIMULATION — IMPLEMENTATION DOCUMENTATION
================================================================================

Purpose: This document is a running technical record of the simulation's
architecture, design decisions, and the rationale behind each significant
change. It is structured for direct use as source material when drafting the
thesis (per-section paraphrasing rather than verbatim quotation). Updated
continuously as the implementation evolves.

================================================================================
1. PROJECT OVERVIEW
================================================================================

The simulation models the Wiener Neustadt railway shunting yard as a discrete-
event simulation (DES) implemented in C# / .NET 8. It is a FLAT shunting yard:
trains arrive, are physically broken apart and re-sorted by destination on
classification tracks, recombined into outbound trains, and depart. The model
captures activity lifecycles, finite resources (workers, locomotives, the
passage track between yard areas, the exit gate), worker travel times, and
worker skill multipliers.

Two artifacts:

  * Simulation engine: C# project producing a CSV event log per run.
  * Visualizer: standalone HTML5 / JavaScript page (SimulationVisualizer.html)
    that replays the CSV log over a yard background image, animating trains,
    wagon groups, workers, and locomotives.

================================================================================
2. HIGH-LEVEL ARCHITECTURE
================================================================================

The simulation follows a hierarchical control-unit pattern (see Furian et al.
2015 for the conceptual framework). Three control units coordinate, each
responsible for a distinct phase of the yard's operation:

  * ArrivalControlUnit
      - Receives inbound trains, queues them, assigns arrival tracks, runs the
        sorting algorithm (destination -> classification track), requests ITP
        (Incoming Train Preparation), and finally PushOff.

  * ClassificationControlUnit
      - Receives wagon groups (WGs) on classification tracks after PushOff,
        decides Securing vs Coupling per arrival, runs the train-completion
        check, instantiates OutboundTrain entities, and runs OBTP and DEPD.

  * ResourceControlUnit
      - Centralized broker for all finite resources: workers, shunting
        locomotives, train locomotives (effectively infinite), the passage
        track, and the exit gate.
      - All activity resource needs flow through SubmitRequest. Returns are
        delayed by travel time (workers ~80 m/min, shunt locos ~25 m/min,
        train locos ~80 m/min) to model realistic walk-back / drive-back.

Engine: SimulationEngine schedules callbacks against simulated time. Activities
register OnReadyToCommence and OnCompleted callbacks that are invoked when
allocated resources arrive and when the activity's calculated duration elapses.

================================================================================
3. ENTITY MODEL
================================================================================

Train (inbound)
  - ID, Length, WagonGroupIds, HasLoco, LocomotiveId, Status, Designation, Time

WagonGroup
  - Id, Length, Destination, WagonIds, CurrentTrackId, CurrentArea, ArrivedAt
  - Belongs to a parent inbound Train at first; after a successful sort and
    PushOff, becomes a standalone entity on a classification track.

OutboundTrain
  - Id (format: "OBT{ddMMyyHHmmss}-{Destination}")
  - Destination, CurrentTrackId, CurrentArea, WagonGroups (list reference,
    not copy — same WagonGroup instances continue to exist), TotalLength,
    TotalWagonCount, LocomotiveId, LeavingPreparationComplete
  - Created the moment a classification track's accumulated WG length crosses
    MIN_TRAIN_LENGTH (currently 100 m).

Worker (WorkerDto)
  - Id, Name, MovementSpeedMetersPerMinute, Skills (per-activity multiplier),
    Area ("Arrival" / "Classification" / null = wildcard).

ShuntingLocomotive (ShuntingLocomotiveDto)
  - Id, MaxSpeed.

Track
  - StationId, RealLifeID (display name like "615"), Length, Area (canonical
    short form: "Arrival" or "Classification"), Designation, Reserved,
    CurrentOccupancies, SegmentIds.

================================================================================
4. ACTIVITY MODEL
================================================================================

All activities derive from the abstract Activity base class. The base class
owns the canonical lifecycle:

  * Submitted    — emitted in the constructor when the activity is instantiated.
  * Started      — emitted by MarkCommenced(now), called when allocated
                   resources have arrived and the work physically begins.
                   Idempotent (guarded against double calls).
  * Completed    — emitted by MarkCompleted(now), called when the activity's
                   calculated duration has elapsed. Idempotent.

Each lifecycle event writes one row to the CSV via SimulationLogger.LogActivityEvent
with the format:

    <simTime>;ActivityEvent;<activityId>;<activityType>;<status>|<details>

Status is "Submitted", "Started", or "Completed" (plus "PassageClaimed" /
"PassageReleased" for the passage-track resource).

Activity ID format:  Act_<ABBR>_<EntityId>_<HHMMSS>_<Location>
Example:             Act_ITP_11001_090500_703

Abbreviation table:
  ARRD = ArrivalDrive
  ITP  = IncomingTrainPreparation
  PO   = PushOff (parent)
  POD  = PushOffDrive (sub-activity)
  SEC  = Securing
  COP  = Coupling
  OBTP = OutboundTrainPreparation
  DEPD = DepartureDrive

Per-activity attributes (RequiredWorkers, RequiresLocomotive, BaseSecondsPerMeter,
LocoStaysWithEntity, WorkersReleasedIndividually) are declared on the subclass.

Activity flow per inbound train:
  Entry (queue)
   -> ArrivalDrive (variable: per-arrival-track distance / 20 km/h + length
      penalty — see [18] and [20])
   -> IncomingTrainPreparation (workers + shunt loco; loco is kept by activity
      after completion via LocoStaysWithEntity=true so it carries over to PO)
   -> PushOff (workers + carried-over loco + passage track)
        -> n × PushOffDrive sub-activities (one per consecutive same-destination
           group; variable: (arrival-track->decoupling + decoupling->class-track)
           distance / 15 km/h + cut-length penalty (group, not whole train)
           — see [20])
   -> Train graphic dismantled; each WG now standalone on classification track

Activity flow per WagonGroup on classification track:
   ArrivedClassificationTrack (instantaneous)
   -> Securing OR Coupling (workers; SEC if first on track, COP if joining)
   -> Completion check (length threshold)
   -> If threshold met: become part of a new OutboundTrain entity
   -> OutboundTrainPreparation (2 workers + train locomotive)
   -> DepartureDrive (exit gate; variable: per-class-track distance to exit
      gate / 20 km/h + length penalty — see [20])
   -> Departed; track unreserved

Worker time multiplier:
  Activity duration = EntityLength × BaseSecondsPerMeter × AverageWorkerMultiplier
  AverageWorkerMultiplier averages each allocated worker's skill multiplier
  for the activity type (default 1.0 if no skill entry).

================================================================================
5. RESOURCE MODEL
================================================================================

ResourceControlUnit owns and arbitrates all shared resources:

5.1 Workers
  - Stored in _availableWorkerIds (HashSet).
  - Partitioned by yard Area: a worker's Area must equal the activity's Area
    (case-insensitive). Empty area on either side acts as a wildcard for
    backward compatibility.
  - Travel: worker leaves the resting area on TravelStarted, arrives at the
    track after FixedTravelDistanceMeters (100 m) / worker's speed. Releases
    after activity ends with travel back to the area.
  - Worker pool size in the current ResourcePool.json: 10 workers split 5/5
    between Arrival and Classification. Rationale: a real classification
    track is ~800 m long, so workers walking from one yard area to the other
    to satisfy a single activity is unrealistic; in practice, workers are
    localized per area. (User's supervisor confirmed.)

5.2 Shunting Locomotives
  - Finite pool (5 in current data).
  - Travel at LocoSpeedMetersPerMinute (25 m/min, slower than workers).
  - Carry over from ITP into PushOff (LocoStaysWithEntity=true on ITP).
  - Released back to pool at PushOff completion.

5.3 Train Locomotives
  - Effectively infinite (100 IDs initialized: TL001..TL100).
  - Allocated for OutboundTrainPreparation only.
  - Travel at 80 m/min (matches fastest workers).
  - Returned to pool when an outbound train departs (ReturnLoco call).

5.4 Passage Track (single-instance shared resource)
  - In a flat shunting yard there is exactly ONE physical track that connects
    the arrival group to the classification group; every PushOff uses it.
  - Implemented as a boolean _passageTrackAvailable in ResourceCU.
  - Required exclusively by PushOffActivity. Held for the ENTIRE PushOff
    (from first sub-drive request through last sub-drive completion) — not
    just per individual drive — because the loco pulls the train back to the
    arrival side between sub-drives, still occupying the passage.
  - On allocation, ResourceCU emits an ActivityEvent with status "PassageClaimed".
    On release, "PassageReleased". The visualizer reads these to drive the
    on-screen passage strip indicator (green = available, red = used by trainId).

5.5 Exit Gate
  - Single-instance shared resource for DepartureDriveActivity.
  - Pre-existing; behavior mirrors the passage track but no travel time.

5.6 Allocation algorithm (TryAllocateAndDispatchResources)
  - Up-front feasibility check (workers, loco, train loco, passage). If any
    requirement is unmet, returns false and the request is queued.
  - Workers are filtered by Area BEFORE the count check, so an Arrival
    activity cannot consume Classification workers and vice versa.
  - On success: workers/locos depart immediately for the work site (with
    travel-time scheduling for arrival callbacks). Activity commences when
    all required resources have arrived (RecordWorkerArrival /
    RecordLocoArrival fires CheckAndTriggerCommencement).

5.7 Queue dispatch policy: FIFO-with-bypass
  - Initially the queue used Peek + Dequeue-on-success. This caused a
    pseudo-deadlock: a request stuck on an unavailable resource (e.g., ITP
    waiting on a busy shunt loco) blocked every later request behind it,
    even those whose own resources were currently available.
  - Replaced with a walk-the-whole-queue policy: copy pending to a list,
    clear the queue, iterate; grant whatever can be granted now, re-enqueue
    the rest in their original relative order.
  - Strictly speaking this is no longer pure FIFO — request B can run before
    request A if A is currently infeasible. This matches what a human
    yardmaster would do (match free resources to whichever feasible job is
    next) and is more realistic than letting expensive resources sit idle
    waiting on one stuck job.

================================================================================
6. WITHIN-TRACK FIFO FOR SEC / COP
================================================================================

Problem observed: when two WGs arrive on the same classification track close
in time, the second one would sometimes start its SEC/COP before the first.
Two roots:
  (a) FIFO-with-bypass at ResourceCU could grant a later request first if the
      earlier one was momentarily infeasible.
  (b) Worker travel-time variance: workers allocated for B might happen to
      arrive sooner than those allocated for A.

Fix in ClassificationCU: per-track gating.
  - _hasLiveSecCopByTrack[trackId]: true when a SEC/COP for that track has
    been submitted to ResourceCU but has not yet emitted Started.
  - _deferredPrepsByTrack[trackId]: queue of arrival requests held while the
    gate is closed.
  - HandleWagonGroupArrival: if the gate is closed for the track, defer this
    WG locally instead of submitting. Otherwise mark the gate as held and
    submit immediately.
  - CommenceAndScheduleActivity (SEC/COP): after MarkCommenced, call
    ReleaseNextDeferredPreparation(trackId, now). That helper opens the gate,
    pops one deferred WG (if any), submits it, and re-closes the gate.

Effect: B's SEC/COP cannot even reach ResourceCU until A's SEC/COP has
Started, so neither bypass nor travel-time variance can flip the order.
Across-track parallelism is untouched — different tracks have independent
gates.

================================================================================
7. OUTBOUND TRAIN COMMITMENT — RELEASING THE DESTINATION-TRACK MAP
================================================================================

Problem observed: ArrivalCU sets _destinationToTrackMap[destination] = track
the first time a destination is sorted. Once a classification track has
accumulated enough WGs and an OutboundTrain is created on it, the train is
committed to that track for OBTP/DEPD (which can take ~30+ minutes). During
that window, additional WGs of the same destination were still being sorted
to the same track and pushed there, even though the track was committed.
Result: the visualizer showed independent populations of WGs on the same
track — some part of the OBT (in OBTP), some not (in their own SEC/COP).

Fix:
  * ClassificationCU exposes a public event:
      DestinationCommittedToOutbound(destination, trackId)
    fired the moment CreateOutboundTrain runs.
  * ArrivalCU has a public method ReleaseDestinationMapping(destination) that
    drops the destination -> track binding.
  * Program.cs wires the two after both CUs are constructed.

After the event fires, the next WG of that destination triggers a fresh
RunSortingMethod lookup and is assigned a different (still-free)
classification track.

Additional fix in CompleteDepartureDrive: the classification track is now
also unreserved (track.Reserved = false), not just emptied. Without this,
each track ever used by an OBT stays reserved forever — fine before this
change because every destination kept reusing its single track, but
post-change with track cycling the simulation would run out of unreserved
tracks.

Defensive null-check in RunSortingMethod: if no free classification track
exists, the WG is skipped (logged as ClassificationTrackUnavailable in the
CSV) instead of NRE'ing. RequestPushOff filters out unassigned WGs from the
PushOff list so the rest of the train can still be processed.

RESOLVED (see [13]): destination tracks are now resolved late, per
sub-push, via ArrivalCU.ResolveTrackForDestination. PushOffActivity no
longer reads from the frozen sort-time wagonGroupToTrackMap; it groups
WGs by destination NAME and asks ArrivalCU for the current track at the
moment each sub-drive fires. So a destination committed to an OBT
between sort time and push time (or between two sub-pushes within the
same PushOff) gets a fresh classification track for any subsequent WGs
of that destination instead of piling onto the now-committed track.

================================================================================
8. SIMULATION LOG (CSV) FORMAT
================================================================================

The log is a single semicolon-separated CSV file written to
bin/Debug/net8.0/OutputFiles/SimulationLog.csv.

8.1 Metadata block (one-time, at the top of the file)

    #META;ResourcePool;v1
    #META;GeneratedAtUtc;<iso8601 utc>
    #WORKER;<id>;<name>;<speedMetersPerMinute>;<area>
    #SHUNTLOCO;<id>;<displayName>;<speedMetersPerMinute>
    #CAPACITY;TrainLocomotives;100
    #CAPACITY;ExitGate;1
    #ENDMETA

  * #WORKER's <area> field is "Arrival" / "Classification" / "" (empty =
    wildcard, back-compat for old data files).

8.2 Event rows

  Column order varies by event type. Layout:

    TrainEvent       : <simTime>;TrainEvent;<actionName>;<entityId>;<details>
    ActivityEvent    : <simTime>;ActivityEvent;<activityId>;<activityType>;<status>|<details>
    WorkerEvent      : <simTime>;WorkerEvent;<entityId>;<actionName>;<details>
    WagonGroupEvent  : <simTime>;WagonGroupEvent;<entityId>;<actionName>;<details>

  ActivityEvent statuses: Submitted, Started, Completed, PassageClaimed,
  PassageReleased.

  Common WorkerEvent actions (used for both workers and locos):
    Allocated, TravelStarted, Arrived, ReturnStarted, Returned.

  Common WagonGroupEvent actions:
    PushingToTrack, EntityCreated, ArrivedClassificationTrack,
    SecuringRequested, SecuringStarted, Secured,
    CouplingRequested, CouplingStarted, Coupled.

  Common TrainEvent actions:
    Entry, AssignedArrivalTrack, ArrivedArrivalTrack,
    ClassificationTrackAssigned, PreparationRequested, PreparationStarted,
    PreparationComplete, PushOffRequested, PushOffComplete, ExitedSystem,
    OutboundTrainCreated, OBTPRequested, OBTPStarted, OBTPComplete,
    DEPDRequested, DEPDStarted, Departed,
    ClassificationTrackUnavailable.

================================================================================
9. VISUALIZER ARCHITECTURE
================================================================================

Single-page HTML/JS file (Output/SimulationVisualizer.html). User uploads the
CSV, the page parses it, and on Play replays events at a configurable
multiplier (1x to 200x).

9.1 Coordinate system
  Background image is 1920x1080, painted with background-size: 1920px 1080px
  and background-position: bottom left. The image is bottom-anchored, so when
  the viewport is taller than 1080 px the top of the image moves UP relative
  to the container origin. Every layout point uses image-space coordinates,
  which are converted to container-space by:

      applyImageYOffset({x, y}) -> { x, y + (container.clientHeight - 1080) }

  This keeps the visualization stable across viewport heights without
  requiring CSS scaling that would distort the image.

9.2 Track positions
  arrivalTrackPositions and classificationTrackPositions are dictionaries
  mapping track real-life IDs to {x, y} anchor points. Workers / locos / WGs
  / standalone WGs all derive their on-track positions from these anchors.

9.3 Slot pool for grid-resident icons
  Workers and shunt locos reside in two grids on the map's left and right
  margins. Each grid is a fixed 2-row layout with explicit slot coordinates
  (R*100 + col, where R=1 is the top row). Whichever icon returns to the
  area first claims slot 101; later returners get 102, 103, etc. Slots are
  released on departure to a track and re-claimed on return — so there is
  no permanent worker-to-slot binding (closer to real shunters' shared rest
  area than a fixed seating chart).

9.4 Worker icons by area
  workerIconForArea(area) returns the right PNG:
    - "arrival"        -> worker_icon_arrival_green.png
    - "classification" -> worker_icon_classification_orange.png
    - empty/anything   -> worker_icon.png (back-compat / wildcard)
  Visualizes the area split at a glance.

9.5 Train graphic
  - Drawn as a flex-row container right-anchored at the arrival track's pos.x
    so the L (locomotive) box sits exactly on the track point. Wagon groups
    flow leftward from the L.
  - Status pill is absolute-positioned above the train (bottom: 100%; left: 50%;
    transform: translateX(-50%)) so it stays centered above the wagons
    regardless of train length.
  - During IncomingTrainPreparation the L box is hidden (visibility: hidden)
    so the shunt loco icon visually "replaces" the original locomotive,
    matching the physical swap.
  - Wagon groups carry data-wg-id; on each EntityCreated event for a WG
    pushed to a classification track, that wagon's div is removed from the
    train AND the train's CSS left is recomputed so the L stays anchored
    at pos.x. This makes the train shrink visibly as PushOff progresses,
    rather than disappearing all at once at PushOff completion.

9.6 Standalone wagon groups (post-PushOff)
  When a WG arrives on its classification track, drawWagonGroupOnClassificationTrack
  creates a standalone .wagon-group.wg-standalone div with full borders,
  positioned right-anchored at the track's pos.x and stacking leftward so
  successive arrivals "park behind" earlier ones. Each carries a small status
  pill below it (.wg-status), driven by a fan-out from ActivityEvent rows:
    SEC/COP -> single WG (entityId == wgId)
    OBTP/DEPD -> all WGs on the activity's location track (fan-out via
                  findWagonGroupsOnTrack — these activities target the
                  outbound train, but visually we light up the constituent
                  WGs).
    PushOffDrive -> explicitly excluded from the fan-out, since the WG
                    isn't yet on the classification track when the drive
                    is in flight.

9.7 Passage strip indicator
  A small (~2.5 cm) horizontal strip on the map between the two yard areas,
  with a status pill above it. Driven by the ActivityEvent rows with status
  PassageClaimed / PassageReleased. Green strip + "Available" pill when free,
  red strip + "Used by <trainId>" pill when held.

9.8 Train status pill
  Floats centered above the train. Possible states: "Waiting" (default), the
  current activity name (e.g., "IncomingTrainPreparation", "PushOff"), or
  "Driving to track <id>" while the train is still moving from the queue.

9.9 findTrainForActivity (badge bubbling rules)
  Maps an activity ID to the trainId whose status pill it should drive.
  Only direct trains[entityId] hits resolve. WG-targeting activities
  (SEC/COP/PushOffDrive) and OBT-targeting activities (OBTP/DEPD) deliberately
  return null, so the train pill is not overwritten with WG-level statuses
  during PushOff. The earlier wagon-group fallback was REMOVED for exactly
  this reason — it caused the train pill to flip to "Securing" or "Coupling"
  while PushOff was still running, which was misleading.

9.10 Destinations legend
  Compact, anchored in image space (top edge at image y=300, x ~ 1255 — under
  the first column of the shunt-loco grid). Repositioned by positionLegend()
  on DOMContentLoaded, on window resize, and on CSV load (the last is
  required because main-content is display:none until the first load, so
  clientHeight is 0 and the image-y offset is wrong without it).

9.11 Sim clock
  Displays full date and time: "DD/MM/YYYY HH:MM:SS". Format chosen to match
  the simulation's Console.WriteLine timestamps so cross-referencing CSV rows
  or console output is direct.

10. DESIGN DECISIONS — RATIONALE FOR THE THESIS
================================================================================

This section records WHY decisions were made, not just WHAT was done.

10.1 Hierarchical control units (per Furian et al. 2015)
  Three CUs separate the lifecycle into clean responsibility boundaries:
  inbound side, classification side, and a centralized resource broker. Each
  CU's queues and state are independent; the only cross-CU communication
  paths are the train hand-off and the resource broker. This makes the
  simulation extensible — adding a new activity or resource type touches
  only the CU that owns its lifecycle.

10.2 Canonical three-timestamp activity lifecycle
  Every activity instance has Submitted / Started / Completed in the CSV.
  Implemented as a base-class invariant rather than per-subclass code, so
  no future activity type can "forget" to emit one. Provides a
  three-timestamps-per-activity dataset usable for waiting-time analyses.

10.3 Worker area split (Arrival vs Classification)
  Real classification tracks are ~800 m long; expecting a single worker to
  walk between yard areas mid-shift to fill a SEC/COP slot is unrealistic.
  Workers in real yards are localized to one side. Implemented by adding
  Area to WorkerDto and filtering at allocation time. Empty-area workers
  remain wildcards for backward compatibility with old data files.
  (User's supervisor explicitly confirmed this matches operational practice
  and that finer-grained per-track assignment is too detailed for this
  project.)

10.4 Passage track as single-instance resource
  The flat shunting yard's neck — the single track between the arrival and
  classification groups — is a real physical bottleneck. Modeling it as a
  shared-capacity-1 resource captures the fact that two PushOffs cannot
  proceed concurrently; the loco of train T1 occupies the neck during both
  the push (forward) and pull-back (between sub-drives). Held for the entire
  PushOff lifecycle, not just per individual drive. Released in
  ResourceCU.Release alongside the worker/loco return path.

10.5 FIFO-with-bypass queue dispatch
  Strict FIFO with a single Peek+Dequeue creates pseudo-deadlocks: one
  infeasible request blocks the entire queue. Walking the whole queue and
  granting whatever's grantable matches what a real dispatcher does and
  measurably improves throughput. Strictly, the model is no longer pure
  FIFO — but the only deviation is that infeasible requests get skipped
  in favor of feasible ones, which is exactly the human dispatcher's
  policy.

10.6 Within-track FIFO for SEC/COP
  Worker travel-time variance and the FIFO-with-bypass change combined to
  occasionally let a later-arriving WG's COP start before an earlier
  WG's SEC. Since classification activities are physically sequential (you
  cannot couple to an unsecured WG), arrival order on a single track must
  be preserved at the COMMENCEMENT level. Implemented as a per-track gate
  in ClassificationCU; release on the previous activity's Started event.
  Across-track parallelism is untouched.

10.7 OBT commitment and destination-map release
  Once an OutboundTrain is created on a track, that track is "committed"
  for the duration of OBTP+DEPD. New WGs of the same destination must be
  routed elsewhere (real dispatchers reassign tracks). Implemented as an
  event from ClassificationCU back to ArrivalCU. Tracks are unreserved on
  DEPD completion so they can be reused by any future destination.

10.8 Defensive null-check for unassigned WGs
  Side effect of (10.7): faster track cycling means more chance of running
  out of free classification tracks. The pre-existing NRE in
  RunSortingMethod was replaced with a clear log + a CSV
  ClassificationTrackUnavailable event + filtering of the affected WG out
  of the PushOff list. The simulation degrades gracefully instead of
  crashing on this edge case.

10.9 Image-space coordinate system + bottom anchor
  Earlier the visualizer used background-size: cover with viewport-relative
  coordinates, which broke alignment whenever the viewport aspect ratio
  changed. Switching to a fixed 1920x1080 image with bottom-anchor and an
  applyImageYOffset helper means every painted element shifts together
  when the viewport changes — alignment is preserved across resolutions.

10.10 Slot-pool grid for workers/locos
  Slots are claimed first-free rather than fixed per worker. Mirrors a real
  rest area where the next-available shunter takes the next-available task
  rather than each having a private locker. Also produces visually pleasant
  packing without per-worker layout configuration.

11. ISSUE LOG (BUGS FOUND AND FIXED)
================================================================================

11.1 Activity lifecycle was incomplete
  Some activities never set CommencedAt (e.g., Coupling, Securing, OBTP,
  DEPD, individual PushOff drives). The CSV was missing Started rows for
  those activities, breaking any waiting-time analysis. Fixed by introducing
  MarkCommenced/MarkCompleted on the Activity base class and routing every
  CU through them. Sweep verified no direct CommencedAt/CompletedAt writes
  remain.

11.2 Worker travel was instantaneous
  Workers used to become available again the instant their activity
  completed, with no return-travel time. Fixed: ReturnStarted is logged at
  release, and CompleteWorkerReturn fires after worker-specific travel time
  to actually return them to the pool. Same pattern for shunt and train
  locos.

11.3 Train's L locomotive box overlapping shunt loco icon
  Visual: when the shunt loco arrived during ITP, its icon parked exactly
  where the train's black "L" box was, doubled-up. Fixed by hiding the L
  box's visibility on ITP Started — physically the train loco is being
  swapped out for the shunt loco at exactly that moment, so the visual
  matches reality.

11.4 Train graphic stayed intact through full PushOff
  Each WG appeared on its classification track but ALSO remained drawn on
  the arrival train. Fixed: on each EntityCreated event, the matching WG
  div is removed from the train and the train's CSS left is recomputed so
  the L stays anchored. Train shrinks visibly as PushOff progresses.

11.5 Head-of-line blocking in ResourceCU's queue
  Strict FIFO with Peek+Dequeue blocked the entire queue if the head
  request was infeasible. Replaced with FIFO-with-bypass (see 10.5).

11.6 Worker travel-time variance flipping SEC/COP order
  Within-track FIFO ordering wasn't guaranteed when workers had different
  speeds. Fixed by per-track gating in ClassificationCU (see 10.6).

11.7 Train pill bubbling to Securing during PushOff
  findTrainForActivity had a fallback that scanned all trains' wagonGroups
  for a wgId match; this caused SEC/COP/PushOffDrive Started events to add
  themselves to the parent train's activeActivities stack, overwriting
  PushOff. Fix: removed the fallback. Only direct trains[entityId] hits
  resolve to a train now. WG fan-out for WG badges is a separate code
  path (findWagonGroupsForActivity) and is unaffected.

11.8 PushOffDrive WG fan-out hitting bystander WGs
  findWagonGroupsForActivity fell back to findWagonGroupsOnTrack(location)
  for unknown entities, which lit up earlier-parked WGs on the same track
  with "PushOffDrive" even though their work was complete. Fix: explicitly
  exclude PushOffDrive from the WG fan-out.

11.9 Destination-track mapping never cleared
  See section 7. Fixed via DestinationCommittedToOutbound event.

11.10 Track.Area was "ArrivalArea" / "ClassificationArea"
  The Track entity copied segment.RailwayStationArea verbatim from the
  infrastructure JSON. Activities created with area = arrivalTrack.Area
  therefore had area="ArrivalArea", which never matched workers tagged
  area="Arrival". Symptom: workers never moved, simulation froze right
  after ArrivalDrive completion. Fix: hard-code Track.Area to the canonical
  short form ("Arrival" / "Classification") in CreateArrivalTracks /
  CreateClassificationTracks. The Where filters that read
  segment.RailwayStationArea directly are unaffected.

11.11 Legend disappeared after refactor

[20] Variable PushOff-drive and DepartureDrive durations (path-distance +
     realistic yard speeds); ArrivalDrive speed corrected
  Extends the entry-[18] philosophy (distance is the BIG weight) to the two
  remaining flat-duration drives — PushOffDrive and DepartureDrive — and
  corrects the unrealistically slow ArrivalDrive speed. All distances are
  exact Euclidean polyline lengths summed from the UTM node coordinates
  (Easting/Northing, metres) in Infrastructure_WienerNeustadt_V20.json.

  Method validation: reconstructing each stored TrackSegment.Length from the
  same node coordinates (ConnectionPoint1 -> InterimPoints -> ConnectionPoint2)
  reproduces the stored value to < 0.5 m on every segment tested (12/12 within

  The supplied node paths are sparse waypoints, so the polyline slightly cuts
  corners on curved track, but curvature contributes < 0.5 m even on 300 m
  segments — negligible.

  20.1 PushOff drive — two-leg distance model
    A real push-off drive runs in two legs meeting at the single decoupling
    point (node 172): (1) arrival track -> decoupling point, depending on
    where the train came from; (2) decoupling point -> destination
    classification track, depending on the resolved target. Total push
    distance = leg1 + leg2. Modeled in PushOffActivity.cs as two static
    dictionaries:
      ArrivalToDecouplingMeters  (arrival track id -> metres, 703..731)
        703/705:193.03  707:165.50  709:139.11  711:111.74  713:84.51
        715:57.70  717:29.68  719:35.20  721:104.62  723:131.97
        725:158.84  727:186.20  729/731:277.92
      DecouplingToClassMeters    (classification track id -> metres, 605..629)
        605:212.40  607:185.37  609:157.84  611:131.32  613:104.40
        615:76.89  617:106.08  619/621:266.93  623:219.02  625:284.72
        627/629:257.39
    The arrival leg is keyed on this.Location (= fromLocation = arrival track
    RealLifeID, set by ArrivalCU); the class leg is keyed on the per-sub-drive
    resolved destinationTrack.RealLifeID. ExecuteNextPush sums the two and
    feeds the result to DrivingActivity.CalculateDrivingDuration instead of
    the previous hard-coded distanceMeters = 100.0. Unknown ids fall back to
    FALLBACK_ARRIVAL_LEG_M (139) / FALLBACK_CLASS_LEG_M (212) — roughly each
    leg's median — so a typo'd id never produces a zero-distance push.
    Resulting full push distances range ~107 m (717->615) to ~563 m
    (729/731->625), versus the old flat 100 m.
    A small length penalty is added on top of travel time
    (PUSH_LENGTH_PENALTY_S_PER_M = 0.2 s/m), applied to the length of the
    WAGON-GROUP CUT being pushed in that sub-drive (group.TotalLength), NOT
    the whole inbound train — each PushOffDrive only propels the consecutive
    same-destination group that decouples at the decoupling point. Final
    push-drive duration:
        duration_s = (leg1_m + leg2_m) / 15 km/h
                   + cut_length_m * PUSH_LENGTH_PENALTY_S_PER_M
    The penalty is applied inline in ExecuteNextPush; the shared
    DrivingActivity.CalculateDrivingDuration stays pure (distance / speed).

    Net result: each run now produces exactly two output files —

    workbook). Build dependency list is one library lighter; runtime is a

  21.2 SimulationLog.csv -> SimulationLog.json (single JSON document)
    The CSV had been useful but had two real problems:
      (a) Column order varied per event type (TrainEvent: SimTime;Type;Action;
          EntityId;Details, ActivityEvent: SimTime;Type;ActivityId;ActivityType;
          Status|Details, etc.), which forced every consumer to maintain a
          per-type positional-decode table.
      (b) Metadata + entity declarations were squeezed into the same file as
          comment-prefixed pseudo-rows (#META, #WORKER, #SHUNTLOCO, #INTRAIN,
          #WAGONGROUP, #OUTTRAIN, #CAPACITY, #ENDMETA) with their own ad-hoc
          column layouts. Adding a field anywhere broke at least one consumer.
    Replaced with a single JSON document written at SimulationLogger.Close():
        {
          "metadata": {
            "generatedAtUtc": "...",
            "workers": [ { id, name, movementSpeedMetersPerMinute, area }, ... ],
            "shuntingLocomotives": [ { id, speedMetersPerMinute }, ... ],
            "capacities": { "trainLocomotives": 100, "exitGate": 1 }
          },
          "entities": {
            "inboundTrains":  { "<id>": { id, arrivalTime, length, wagonGroupIds[], hasLoco, locomotiveId }, ... },
            "wagonGroups":    { "<id>": { id, length, destination, wagonIds[], parentTrainId }, ... },
            "outboundTrains": { "<id>": { id, destination, trackId, wagonGroupIds[], length, totalWagonCount, createdAt }, ... }
          },
          "events": [
            { simTime, type: "TrainEvent",      action, entityId, details },
            { simTime, type: "WagonGroupEvent", entityId, action, details },
            { simTime, type: "WorkerEvent",     entityId, action, details },
            { simTime, type: "ActivityEvent",   activityId, activityType, status, details },
            ...
          ]
        }
    Notable shape choices:
      * Entity dicts are keyed BY ID (not arrays). O(1) lookup in the
        downstream consumers instead of build-an-index loops, and the file
        self-documents the entity registry.
      * Every event field is named — no more "is the third token the entity
        id or the action name?" per-type decoding.
      * Activity 'status' (Submitted / Started / Completed / PassageClaimed /
        PassageReleased / ExitGateClaimed / ExitGateReleased) is its own
        field. Previously it was glued to the details with a '|' separator
        and every consumer had to split.
      * 'details' is still a free-form key=value;key=value string for now.
        This kept the port mechanical — no caller upstream of the logger
        had to change. Promoting it to a structured object is a clean
        follow-up that touches only the logger and the consumers.
      * File is written WHOLE on Close() (not streamed). The sim doesn't
        crash mid-run, and runs complete in seconds-to-minutes; the
        trade-off (a hypothetical crash mid-sim leaves no log) is fine.

  21.3 Logger refactor (Output/SimulationLogger.cs)
    Stream-of-CSV-lines pattern replaced with in-memory buffering:
      * Three Dictionary<string, Dictionary<string,object?>> for inbound
        trains / wagon groups / outbound trains (keyed by id).
      * One Dictionary<string,object?> for the metadata block.
      * One List<Dictionary<string,object?>> for events.

    Initialize() auto-rewrites a .csv extension to .json if any caller
    still passes the old name; harmless safety net.

  21.4 analytics.py refactor (Output/analytics.py)

    parse_train_timeline, parse_obts_and_wgs, parse_wg_yard_times) opened

    Constant rename: CSV_PATH -> LOG_PATH, parameter rename csv_path ->

  21.5 Visualizer refactor (Output/SimulationVisualizer.html)

      M  Queue wait (s)              = (E - D) * 86400

      N  Arrival drive dur (s)       = (F - E) * 86400

      P  ITP duration (s)            = (I - H) * 86400
      Q  PushOff wait (s)            = (K - J) * 86400

      R  PushOff duration (s)        = (L - K) * 86400
      S  Total in arrival yard (s)   = (L - F) * 86400

      T  Total in system (s)         = (L - D) * 86400

  25.2 ITP duration formula now driven by separation joints
    Old formula (length × constant × worker_multiplier):
      duration_s = trainLength × 7 × averageWorkerMultiplier
    This was purely length-driven, so a 200 m train going to one
    destination took the same ~23 minutes as a 200 m train sorted
    into 5 destinations — which doesn't match reality. Workers in
    real life prepare each separation point (loosen couplings,
    brake lines) before push-off, so the number of separation joints
    is the main driver of work time.
    New formula:
      effective_joints = max(separation_joints, 1)
      duration_s = effective_joints
                   × BASE_SECONDS_PER_JOINT      (= 120 s)
                   × (trainLength / REF_LENGTH_M) (= length / 100)
                   × averageWorkerMultiplier
    A separation joint = (number of consecutive same-destination
    cuts produced by sorting) − 1. So a train all going to one
    destination has 0 joints (floored to 1 — even a single-destination
    train needs the loco-decouple + brake-check work that takes
    roughly one joint's time). A train sorted into 3 cuts has
    2 joints. Sample durations with the chosen constants:
      0 joints / 100 m / mult 1.0 →   2.0 min  (1 × 120 × 1.0 × 1.0)
      0 joints / 200 m / mult 1.0 →   4.0 min  (1 × 120 × 2.0 × 1.0)
      1 joint  / 100 m / mult 1.0 →   2.0 min  (1 × 120 × 1.0 × 1.0)
      2 joints / 200 m / mult 1.0 →   8.0 min  (2 × 120 × 2.0 × 1.0)
      3 joints / 250 m / mult 1.0 →  15.0 min  (3 × 120 × 2.5 × 1.0)
      4 joints / 300 m / mult 1.0 →  24.0 min  (4 × 120 × 3.0 × 1.0)
    BASE_SECONDS_PER_JOINT and REF_LENGTH_M are named constants in
    Models/ManipulationActivity.cs — tune either to recalibrate
    without changing formula shape.

[31] Cut (group of wagon groups / WGG) handled as ONE unit on the
     classification track -- spurious internal-coupling fix
  Problem caught from the Classification context column. Two wagon groups
  (1204203, 1204204) that were adjacent in the same inbound train (12042),
  shared a destination (Ljubljana), and were therefore pushed together in
  ONE PushOffDrive, were nonetheless given two separate classification
  activities on the destination track 625: a Securing for 1204203 (first
  onto the empty track) and a Coupling for 1204204 (second).

  31.1 Root cause
    "Cut" defined: a maximal run of CONSECUTIVE same-destination wagon
    groups within an inbound train -- a group of wagon groups (WGG). The
    sort leaves a separation joint only BETWEEN cuts (so the ITP joint
    count is already correct), and PushOff pushes each cut as a single
    PushOffDrive (entity "wg1+wg2+..."). The members of a cut are never
    uncoupled from one another, so they are already coupled when they
    reach the classification track.
    But ClassificationCU had no concept of a cut. PushOffActivity.
    OnPushCompleted called HandleWagonGroupArrival once per member WG, and
    ClassificationCU decided Securing-vs-Coupling per WG ("is the track
    empty?"). For a 2-WG cut landing on an empty track that produced
    SEC(first) + COP(second) -- inventing an internal coupling between two
    groups that were already coupled. Side effects: an extra Coupling per
    multi-WG cut, inflated coupling counts and worker-time, and -- because
    SEC and COP run in parallel (the within-track gate only orders the
    STARTS) with different lengths/durations -- the two members finished
    at different times, giving them different classification timestamps and
    a confusing order in the context column (the shorter Coupling completed
    before the longer Securing).

  31.2 Solution
    A cut is now handled as a single unit on the classification track:
      * PushOffActivity.OnPushCompleted builds all of the cut's WagonGroup
        entities (still logging EntityCreated per WG for the visualizer)
        and hands the whole cut to the new
        ClassificationControlUnit.HandleWagonGroupCutArrival(
        List<WagonGroup>, Track, time) in ONE call.
      * ClassificationCU runs ONE classification activity per cut: a
        Securing if the track was empty when the cut arrived, else a
        Coupling-to-the-standing-rake. The decision is captured at arrival
        (TrackWasEmpty on the request) so a within-track deferral cannot
        flip it. The activity entity id is the "+"-joined cut id
        (Act_SEC_1204203+1204204_...) and its length is the cut total.
        Per-WG WagonGroupEvents (SecuringRequested/Started/Secured,
        Coupling...) are still emitted for EACH member so the visualizer
        lights up the whole cut, and all members share the single
        activity's completion timestamp.
      * Per-track bookkeeping (pending-SEC/COP count, within-track FIFO
        gate, deferred queue) is now keyed per CUT, not per WG. The OBT
        completion check still waits for the pending count to hit zero.
    Renames inside ClassificationCU: HandleWagonGroupArrival ->
    HandleWagonGroupCutArrival; HandleWagonGroupPreparation ->
    HandleWagonGroupCutPreparation; CommenceAndScheduleActivity ->
    CommenceAndScheduleCutActivity; CompleteActivity -> CompleteCutActivity
    (with an idempotency guard); nested WagonGroupPreparationRequest ->
    WagonGroupCutPreparationRequest (carries the cut list, CombinedId,
    TotalLength, TrackWasEmpty).

  31.3 Downstream consumers
    * analytics.py parse_wagon_groups: SEC/COP entity is now split on '+'
      (as PushOffDrive already was), crediting every member WG with the
      shared completion time + type and recording the cut membership. The
      Classification context narrative was rewritten to be cut-aware: WGs
      in one cut report "got secured/coupled" together, note they were
      "already coupled ... from the inbound train", share one timestamp,
      and are never shown coupling to one another. Backward compatible:
      pre-cut logs have single-id SEC/COP entities, which split() returns
      as one-element cuts.
    * SimulationVisualizer.html findWagonGroupsForActivity: splits a
      "+"-joined SEC/COP entity so the running-activity badge lights up
      exactly the cut's members instead of the whole track.

  31.4 Effect on KPIs (expected, after re-running the sim)
    Fewer Coupling activities (only genuine cut-to-rake couplings remain);
    Securing now scales with cut length. Members of a cut get identical
    classification timestamps, so the Wagon Groups "Idle time on
    classification track" and "Time in classification yard" columns become
    consistent within a cut. Coupling duration is still length-based on the
    cut total -- a calibration choice that could be revisited (a single
    cut-to-rake coupling is arguably one interface operation, not length-

[32] ITP duration reformulated (joint work + train-length walk); PushOff
     speed 10 km/h; time-per-joint 90 s
  Calibration changes from a review of the drive / ITP equations workbook
  (Other files/Drive_speed_and_ITP_equations.xlsx).

  32.1 New ITP duration formula
    Old:
      duration_s = max(joints,1) x 120 x (trainLength / 100) x workerMult
    New:
      duration_s = max(joints,1) x BASE_SECONDS_PER_JOINT x workerMult   (joint term)
                   + (trainLength / walkingSpeed) x 60                    (walk term)
    Two physically distinct terms:
      * Joint term: the hands-on separation work at each joint -- uncoupling
        and fitting / removing the removable link that splits the wagon-group
        cuts during push-off. Driven by the separation-joint count (floored to
        1) and the average ITP-skill multiplier of the allocated workers. The
        old length factor (trainLength / 100) is DROPPED -- train length no
        longer scales the per-joint work.
      * Walk term: the time for the workers to walk the length of the train
        for the visual checks / info confirmation done during ITP.
        trainLength (m) / walkingSpeed (m/min) -> minutes, x 60 -> seconds.
    BASE_SECONDS_PER_JOINT reduced 120 -> 90 s.

  32.2 Worker walking speed
    walkingSpeed is the workers' station MovementSpeedMetersPerMinute (the
    SAME speed used for their travel to the work site), averaged across the
    workers actually allocated to the ITP. ArrivalControlUnit computes that
    average from the allocated WorkerDtos and sets
    ManipulationActivity.WalkingSpeedMetersPerMinute before CalculateDuration
    runs; a fallback of 80 m/min is used if no speed is available.
    Realism check (ResourcePool.json): worker speeds span 79-100 m/min =
    4.7-6.0 km/h (mean 85.9; Arrival-area ITP workers mean 87.1), within the
    realistic adult-walking band (~5 km/h average, ~6 km/h brisk). No data
    change needed.

  32.3 PushOff drive speed 15 -> 10 km/h
    PushOffActivity.PUSH_SPEED_M_PER_MIN 250 m/min (15 km/h) -> 166.67 m/min
    (10 km/h), the cautious end of the 10-15 km/h flat-yard shunting band.
    Push-drive durations rise accordingly (travel_s = distance_m x 0.36 at
    10 km/h). ArrivalDrive / DepartureDrive (20 km/h) and the 0.2 s/m length
    penalties are unchanged.

[33] Arrival-track wait: real-clock Thread.Sleep replaced with sim-time
     rescheduling (DES correctness fix)
  ArrivalControlUnit.HandleTrainArrival assigned an arrival track in a
  busy-wait: while (assignedTrack == null) { ...scan tracks...;
  Thread.Sleep(30000); }. Thread.Sleep blocks the REAL wall clock inside a
  single-threaded DES event handler -- so if every suitable arrival track
  is occupied when a train arrives, the handler sleeps the engine thread
  forever: nothing else can run, including the PushOff completion that
  would free a track, and the whole simulation freezes. It only worked
  because the current test schedule never actually contends for arrival
  tracks; any denser / higher-utilisation scenario would deadlock.

  33.1 Fix
    * HandleTrainArrival now delegates to TryAssignArrivalTrack(train),
      which makes ONE assignment attempt. On success it reserves the track,
      removes the train from the entry queue, and starts the arrival drive
      (StartArrivalDrive -- the old drive / sort / ITP-request tail extracted
      verbatim). On failure it logs the wait once and RE-SCHEDULES itself on
      the engine at Now + ARRIVAL_TRACK_RETRY_SECONDS (30 s of SIM time),
      never blocking. The poll advances in sim time, so it is deterministic
      and lets the freed-track event run first.
    * Capacity guard: if NO arrival track is even long enough for the train
      (a data/capacity error, not a transient wait), it is logged as a
      TrainEvent "ArrivalTrackUnavailable" (mirroring the existing
      "ClassificationTrackUnavailable") and abandoned, instead of
      rescheduling forever -- which would keep the engine's event list
      non-empty and stop the run from ever terminating.
    * RemoveFromEntryQueue filters the specific train out of _entryQueue
      (assignment order can differ from arrival order when trains need
      different track lengths), replacing the old blind Dequeue.

  33.2 Behaviour
    Unchanged on the current scenario -- there is no arrival-track
    contention, so the reschedule path is never taken and every train is
    assigned a track on the first attempt exactly as before. The change only
    matters once trains actually compete for arrival tracks. An event-driven
    alternative (re-run assignment from RequestPushOff's track-release site
    instead of polling) is noted in the code comment.

  33.3 Files touched
    Control/ArrivalControlUnit.cs - HandleTrainArrival split into
                                    TryAssignArrivalTrack / StartArrivalDrive /
                                    RemoveFromEntryQueue; Thread.Sleep removed;
                                    capacity guard + ARRIVAL_TRACK_RETRY_SECONDS.
